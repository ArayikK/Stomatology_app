## 2026-09-18 — Project overview from the start

### What Stom is
A Flutter dental-charting app for one clinician (Android / iOS / Windows / macOS / Linux / Web).
Data lives **locally first** in SQLite, with a best-effort cloud backup to a small Node.js backend.

### Layout
| Area | Path | What it does |
|---|---|---|
| Entry | `lib/main.dart` | Opens repo, seeds sample data, starts `HomeScreen` (teal Material 3 theme) |
| Database | `lib/data/app_database.dart` | SQLite schema: `patients`, `tooth_notes`, `tooth_note_history`, `tooth_images`, `patient_relationships`, `appointments` |
| Data access | `lib/data/dental_repository.dart` (572 lines) | All CRUD: patients, family links, notes + history, images/pairing/annotations, appointments, sample seed |
| Cloud sync | `lib/data/backend_sync_service.dart` | `pushAll` (upload everything), `pullAll`, `restoreFromPayload` |
| Identity | `lib/data/device_identity.dart` | Anonymous random device id (no login) |
| Reminders | `lib/data/notification_service.dart` | Local notifications for appointments |
| Chart | `lib/chart/` | Odontogram drawing (tooth paths generated by `tools/gen_tooth_paths.py`) |
| DICOM | `lib/dicom/` | Own DICOM parser + JPEG Lossless (Process 14) decoder for x-ray import |
| Screens | `lib/screens/` | Home, patient list/profile/chart, tooth detail, appointments (1324 lines), image annotation, FAQ, legal |
| Legal | `lib/legal/legal_content.dart` | Privacy / terms text |
| Backend | `backend/` | Express + MongoDB, 2 endpoints: `GET/PUT /api/user/:deviceId`, whole dataset as one JSON doc |
| Tests | `test/` | widget tests, DICOM conversion tests, appointments/timeline tests |
| Ideas | `Responses.txt` | Competitor list + feature ideas |

Size: ~8.5k lines of Dart in `lib/`. Backend: 70 lines.

6. **Web breaks sync.** `backend_sync_service.dart` uses `dart:io File`, which doesn't exist on web.
7. **Sample data seeded in production** (`main.dart` → `seedSampleDataIfEmpty`). Fake patients appear

## 2026-09-18 — "Is there a backend / database at all?"

**Yes, both exist, and the design is already what you want: no registration, data keyed by device ID.**

### How it works today
1. **Device ID** — `lib/data/device_identity.dart`: on first launch the app generates a random UUID
   and saves it in `shared_preferences` (key `stom_device_id`). No login. That ID is the user's identity.
2. **Local database (on the phone)** — SQLite file `stom_dental.db` (`lib/data/app_database.dart`).
   Every screen reads and writes here first, so the app works offline.
3. **Cloud database** — MongoDB Atlas. The connection string is in `backend/.env` (`MONGODB_URI`,
   which is set). Collection `users`: one document per device → `{ deviceId, data, updatedAt }`
   (`backend/models/UserData.js`).
4. **Backend server** — `backend/server.js` (Express), deployed at
   `https://stomatology-app.onrender.com` (set in `lib/data/backend_sync_service.dart`):
   - `PUT /api/user/:deviceId` → saves the whole dataset for that device
   - `GET /api/user/:deviceId` → returns it
5. **Sync** — after edits (adding patients, profile changes), the app calls `pushAll()`, which uploads
   everything to `PUT /api/user/<deviceId>`.

```
Phone: SQLite  --pushAll()-->  Render (Express)  -->  MongoDB Atlas
        ^                                               (users collection,
        +-- device UUID in shared_preferences            1 doc per deviceId)
```

### Checked just now
- `https://stomatology-app.onrender.com/` **did not respond**. It accepted the TCP connection but
  sent no reply within 20-90 s. Other sites load fine from this machine.
  Possible causes (not verified):
  - The Render free service is asleep or starting slowly.
  - The service crashed. For example, if the server can't connect to MongoDB it exits
    (`process.exit(1)`), often because Atlas Network Access doesn't allow `0.0.0.0/0` or
    `MONGODB_URI` isn't set in Render.
  **To verify:** open the Render dashboard → service → **Logs**. You should see
  `Connected to MongoDB` and `Stom backend listening on port ...`.
- Because `pushAll()` swallows every error (returns `false` silently), the app **wouldn't show you**
  if the upload failed. Your data may be only in local SQLite right now.

### Gaps to fix before relying on it
- **The device ID is lost on uninstall** → a new ID → the old cloud data is orphaned. That's fine for
  "no registration", but to bring data to a new phone you'd need a way to show/enter the ID
  (e.g. a "Backup code" in settings) or a QR transfer.
- **No restore button.** `pullAll()` / `restoreFromPayload()` exist but no screen calls them.
- **The upload is partial.** It skips appointments, family links and note history.
- **No auth.** Anyone who knows a device ID can read/overwrite it. A UUID is hard to guess, but add
  at least a shared API key header.
- **No sync status in the UI.** Show "Last backup: …" / "Backup failed" so failures are visible.

## 2026-09-18 — Option 1: keep Render awake (setup steps)

This needs an account on an outside service, which only you can create. Takes ~3 minutes.

### cron-job.org (free, recommended)
1. Go to https://cron-job.org → **Sign up** (email + password) → confirm the email.
2. Dashboard → **Create cronjob**.
3. Fill in:
   - **Title:** `Stom backend keep-alive`
   - **URL:** `https://stomatology-app.onrender.com/`
   - **Execution schedule:** *Every 10 minutes*
4. Open **Advanced** and set **Timeout** to the max (30 s). The first wake-up can be slow; later pings answer in <1 s.
5. **Create**. The history column should show `200 OK` within ~10 min.

(Alternative with the same steps: UptimeRobot → *New monitor* → HTTP(s), same URL, interval 5 min.)

### Check it works
- Wait 30+ min without using the app, then open `https://stomatology-app.onrender.com/` in a browser.
  It should answer **instantly** with `{"status":"ok","service":"stom-backend"}`.
- The Render dashboard → **Logs** shows a `GET /` every 10 min.

### Notes
- Render free = 750 instance-hours/month. One always-on service uses ~720-744, so it fits,
  **as long as this is your only free service** kept awake.
- A GitHub Actions cron in the repo could do the same without a new account, but GitHub often delays
  scheduled runs by 10-30+ min and disables them after 60 days without commits. Less reliable, so not
  chosen.
- The app changes (option 2) are still worth doing as a safety net: startup wake-up ping, longer
  timeout + retry, and a visible backup status.

  Expected: `200 OK` with `{"status":"ok","service":"stom-backend"}`. The first run may be slow or
  time out if the server is asleep. Run it again after a minute and it should be instant.
- ✅ **Done (2026-09-18 19:20 UTC):** the test run with `https://` returned `200 OK` in 549 ms with body

## 2026-09-18 — Option 2 done: the app handles a slow/sleeping backend

### What changed
**`lib/data/backend_sync_service.dart`**
- **Timeout 20 s → 90 s.** A cold Render start was measured at ~72 s.
- **Retry.** Each backup tries up to 2 times before giving up.
- **No parallel uploads.** If edits happen while a backup is running, they don't start a second upload
  at the same time. They queue **one** follow-up upload so the newest data is always sent.
- **Status you can see.** New `status` (`ValueNotifier<SyncStatus>`) with state `idle / syncing / synced / failed`
  and `lastSuccessAt`. The last successful backup time is saved in `shared_preferences`
  (`stom_last_backup_at`), so it survives restarts.
- **`warmUp()`**: loads the saved last-backup time and pings `GET /` so a sleeping server starts
  waking up right away.

**`lib/main.dart`**: calls `syncService.warmUp()` at startup, in the background (doesn't delay app launch).

**`lib/screens/home_screen.dart`**: new cloud icon in the home app bar (`_BackupStatusButton`):

| ☁✓ | Last backup succeeded |

Tap the icon to **back up now**. A snackbar shows "Backup complete" or "Backup failed…".

## 2026-09-19 — App tour (spotlight coach marks)

Built from `Poker_App2/TOUR_PROMPT.md`. **Colors are Stom's own**: everything comes from the app's
teal seed (`kStomSeedColor` in the new `lib/app_theme.dart`). Nothing is taken from the poker app.

### How it works for the user
1. **First launch** → a welcome page (`lib/tour/intro_screen.dart`): a live preview of the dental
   chart, "Every tooth. Every visit.", and two buttons: **Take the tour →** / **Skip for now**.
2. **Take the tour** → dashboard fades in → spotlight tour of the home screen.
3. Every other screen explains itself **the first time you open it** (only if you opted in):
   | Screen | Steps |
   |---|---|
   | Home | 9: day at a glance · practice numbers · Add patient · All patients · Appointments · Today's schedule · Recently seen · Cloud backup · Menu |
   | Patient chart | 3: the chart · allergy warning (*only if the patient has allergies*) · medical history & timeline |
   | Tooth | 4: x-rays & photos · add image (photo/gallery/DICOM) · treatment notes · add note (dictation) |
   | Appointments | 3: agenda/month toggle · Today button · new appointment + reminders |
4. **Skip tour** (top-right chip, or the phone's Back button) closes it **and turns off all remaining
   screen tours**. **Finish** marks just that screen as done.
5. **Menu → "App tour"** replays the home tour and turns the other screens' tours back on.

### Design (per spec, in Stom colors)
- Dark scrim (near-black with a teal tint @ 74%) with a rounded **cutout** around the real widget,
  a glowing teal border (glow drawn *outside* only), a tooltip card with an arrow, "STEP n OF m", a
  progress bar, and a **Next / Finish** button.
- Tour colors are the **dark** variant of the teal palette, so the overlay reads the same in light
  and dark mode (the spec: keep the scrim dark).
- Kept from the spec: the backdrop never flashes between steps (only the hole crossfades); the
  tooltip height is estimated on the first frame and measured after that (never clipped on short
  phones); the tooltip sits below the target, or above if there's no room, and is clamped on screen;
  padding is set per step; the card slides out from its arrow; double-taps are guarded.

### Deviations from the spec (on purpose)
- **Real widgets, not replicas.** The spec recommends this for most apps. Each screen has
  `GlobalKey`s on its real widgets. The keys are permanent, so the spec's "new key every step"
  rule (needed only for replicas) isn't needed.
- **One tour per screen, not one long tour.** A new user can't reach a tooth or chart before a
  patient exists, so each screen explains itself on first visit.
- **Coordinates**: the tour is a transparent route above the screen, not a render ancestor, so
  positions are converted through global coordinates instead of `ancestor: self`.
- **Wide tablets**: the tooltip is capped at 440 px and centered on the target instead of spanning
  the full width.
- **Steps whose target isn't on screen are dropped** before starting, so "STEP n OF m" stays correct
  (e.g. no allergy banner → chart tour has 2 steps).
- The home phone layout changed from a lazy `ListView` to `SingleChildScrollView` + `Column`, so
  every card exists for the tour to scroll to. Only 5 cards, so there's no performance cost.

## 2026-09-19 — "Could not load your practice data." on a friend's phone

### What that screen actually is
`_LoadFailed` in `lib/screens/home_screen.dart`. It has **nothing to do with the cloud** despite the
cloud-off icon: it shows when the *local* SQLite read in `_loadData()` throws — either
`getPatientSummaries()` or `getAllAppointments()`.

We know the app itself started fine on his phone: `main()` runs `seedSampleDataIfEmpty()` *before*
`runApp`, and that reads the `patients` table. If the database could not be opened at all, he'd have
seen a blank screen, not the dashboard. So the database opened and `patients` exists — one of the
**newer tables** is what blew up.

### Root cause (the migration bug from the first review)
`app_database.dart` was on `version: 1` with **no `onUpgrade`**, but the tables kept growing:

| Build | Tables created |
|---|---|
| `77ccc13` initial | patients, tooth_notes, tooth_images |
| `538ab06` | + medical columns on patients, category on tooth_notes |
| `143f1f9` | + tooth_note_history, patient_relationships, appointments |

SQLite only runs `onCreate` when the file doesn't exist. Your friend had an **older Stom APK already
installed**, so his `stom_dental.db` was created by an older build and kept as-is on update — still
"version 1", so nothing re-ran. The dashboard then calls `getAllAppointments()` →
**`no such table: appointments`** → that error screen. Your phone works because your database was
created by a recent build (or you reinstalled clean).

### The fix (done)
**`lib/data/app_database.dart`** — proper migration, and a belt-and-braces repair:
- `version: 2`, and `onCreate` / `onUpgrade` / `onDowngrade` all call the same new
  **`ensureSchema(db)`**.
- `ensureSchema` is idempotent: `CREATE TABLE IF NOT EXISTS` for all six tables,
  `CREATE INDEX IF NOT EXISTS` for all five indexes, and column-by-column `PRAGMA table_info` checks

- `onOpen` runs one cheap `sqlite_master` count and repairs the schema if any of the six tables is

- **No data is lost**: everything is create-if-missing, nothing is dropped or rebuilt.
